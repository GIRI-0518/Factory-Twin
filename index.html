🔄 Discrete-Event Simulation Flow
1 — Source
Stage 1 (Raw Input) pulls from an infinite virtual source. It never starves. It feeds all downstream stages.
2 — Buffer & Backpressure
Units queue in a buffer between stages. A slow stage causes upstream accumulation (backpressure) and downstream starvation simultaneously.
3 — Theory of Constraints
System throughput = slowest stage throughput. Effective cycle time = base / capacity. Bottleneck score combines utilization + buffer depth.

🔍 How the Recommendation Engine Works
Shadow Simulation Process
  1. Clone current simulation state (stages, buffers, tick)
  2. Apply candidate improvement (e.g., +20% capacity)
  3. Fast-forward cloned state for 120 ticks (2 sim-minutes)
  4. Measure predicted throughput from shadow run
  5. Compare against current live throughput
  6. Identify new bottleneck in the improved scenario
Bottleneck Score Formula
score = util_norm × 0.5
      + buffer_norm × 0.5

util_norm = (utilTicks / totalTicks)
buffer_norm = bufLen / maxBufLen

Stage with highest score = bottleneck
3 Candidate Scenarios Evaluated
  • Scenario A: +20% capacity at current bottleneck
  • Scenario B: −20% cycle time at bottleneck (process improvement)
  • Scenario C: +20% capacity at top-2 most-utilized stages
Best predicted throughput gain wins and is shown as primary recommendation.
Dynamic Bottleneck Shifting
After each shadow run, the engine identifies what the new bottleneck would be after the proposed fix is applied. This models the Theory of Constraints "drum-buffer-rope" reality: fixing one constraint simply reveals the next one. The panel always reports the predicted successor bottleneck so operators can plan ahead.

▼

🏗️ Architecture Overview

The application is structured into 4 decoupled modules in script.js:

  • SimEngine — pure simulation state machine, zero DOM access. Runs the discrete-event tick loop.
  • Renderer — reads snapshots from SimEngine, updates the DOM. Never mutates simulation state.
  • Controls — maps UI events (sliders, buttons) to SimEngine parameter mutations.
  • RecommendationEngine — runs shadow simulations, scores scenarios, returns plain objects for Renderer to display.

⏱ Tick Loop & Timing

A setInterval fires every 200ms (adjustable). Each interval = 1 simulated second. The tick loop processes every stage in two passes:

  • Pass 1 (reverse order): Push completed units to the next stage's buffer, or to "completed output" for the last stage. Reverse-order prevents cascading within a single tick.
  • Pass 2 (forward order): For each idle stage with input available and capacity > 0, dequeue a unit and start processing. Set busyUntilTick = tick + cycleTime / capacity.

📏 Bottleneck Detection Logic

Every tick, each stage receives a bottleneck score:

  • utilNorm = utilizationTicks / totalTicks — how busy the stage has been
  • bufNorm = bufferLength / maxBufferLength — relative queue depth
  • score = utilNorm × 0.5 + bufNorm × 0.5 — combines both signals with equal weight
  • Stage with the highest score is labeled the bottleneck and highlighted in red

This dual-signal approach catches both high-utilization bottlenecks (fast machine, overloaded) and buffer-accumulation bottlenecks (slow machine causing upstream backup). The bottleneck label updates every tick — it will shift automatically when conditions change.

🌊 Theory of Constraints Enforcement

The system naturally enforces ToC without any special check: since each stage can only consume one unit at a time and units flow sequentially, the slowest active stage dictates the maximum downstream flow rate. If you reduce Stage 3's capacity, its effective cycle time rises, its output buffer shrinks, and all later stages enter a "starved" state. Simultaneously, Stage 3's input buffer grows from upstream overproduction.

🧠 Recommendation Engine (Shadow Simulation)

Every 5 seconds, a background analysis runs:

  • Deep-clone all stage state (buffers, counters, busy timers)
  • Apply a candidate parameter change (e.g., bottleneck capacity +20%)
  • Run the cloned state forward for 120 ticks entirely in-memory — no UI updates, no side effects
  • Measure resulting throughput from the shadow run
  • Compare all 3 candidate scenarios; display the highest-gain option as the recommendation
  • Identify what the new bottleneck would be in the improved scenario

All numbers shown (before/after throughput, % improvement, new bottleneck utilization) are derived from these shadow simulation runs — not guesses or heuristics.

📊 Metrics Computed

  • Throughput: units completed in last 60-tick window × (60/windowSize) = units/min
  • Utilization %: (utilizationTicks / totalTicks) × 100
  • Buffer length: current queue size (count of waiting units)
  • Starved time: ticks where stage had no input
  • Blocked time: ticks where downstream buffer exceeded 20 units
🔬 Key Equations
Effective Cycle Time
effectiveCT = cycleTime / capacity
e.g. 9s / 0.5 capacity = 18s/unit

busyUntilTick = currentTick + effectiveCT
Throughput (units/min)
windowUnits = completed[now] - completed[now-60]
tpPerMin = (windowUnits / windowTicks) × 60

1 tick = 1 sim-second → 60 ticks = 1 sim-min
Bottleneck Score
utilNorm = utilizationTicks / totalTicks
bufNorm = bufferLen / maxBufferLen
score = utilNorm×0.5 + bufNorm×0.5
Shadow Simulation TP
shadowRun(overrides, N=120 ticks)
newUnits = shadowCompleted - liveCompleted
shadowTP = (newUnits / N) × 60 u/min
